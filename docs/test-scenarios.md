# Тестовые сценарии (end-to-end)

Проверяются на чистой базе: `docker compose down -v && docker compose up --build`
или локально после удаления `data/`. Демо-данные создаются автоматически.
Учётные записи: клиент — PIN `1234`, банк — PIN `0007`.

## Сценарий 1 — Happy path: заявка → одобрение → выдача (основной)

| Шаг | Действие | Ожидаемый результат |
| --- | --- | --- |
| 1 | Войти в «Клиентский кабинет» (PIN 1234) | Кабинет открыт, видны демо-заявки |
| 2 | «Новая заявка»: ООО «Ромашка», ИНН 7700123456, продукт «Оборотное финансирование», 2 400 000 ₽, 18 мес., выручка 18 000 000 ₽ | В правой колонке показаны платёж, переплата, DTI, ориентир по сумме — расчёт обновляется до отправки |
| 3 | «Создать и отправить заявку» | Заявка `ALF-26-000X` в статусе «Отправлена»; запись в истории: `APPLICATION_SUBMITTED` |
| 4 | «Рабочий кабинет банка» (PIN 0007), роль «Аналитик», найти заявку | Заявка в очереди, индекс качества высокий, блокирующих сигналов нет |
| 5 | «Запустить демо-проверки» | Статусы прошли VALIDATION → ENRICHMENT → SCORING → MANUAL_REVIEW; в «Источниках» — mock-ответы ЕГРЮЛ/ФНС/БКИ |
| 6 | Сменить роль на «Старший аналитик», открыть «Действия» | Доступна форма решения (решение — только из MANUAL_REVIEW) |
| 7 | Зафиксировать «Одобрена», основание ≥15 символов | Статус «Одобрена», условия зафиксированы в карточке решения |
| 8 | В клиентском кабинете найти заявку | Блок «🎉 Одобрено» с условиями; кнопки «Принять предложение и продолжить» / «Отклонить предложение» |
| 9 | Нажать «Принять предложение и продолжить» | Статус «Предложение принято клиентом» (ACCEPTED) |
| 10 | «Получить код подписания» | Показан демо-код из 4 цифр (имитация SMS), TTL 15 минут |
| 11 | Ввести код, «Подписать предложение» | Статус «Подписана» (SIGNED); неверный код не проходит с сообщением об ошибке |
| 12 | «Получить кредит (демо-выдача)» | Статус «Выдана» (DISBURSED); показан демо-счёт, сумма, дата; в аудите — `LOAN_DISBURSED` |

Данные между шагами не теряются: после каждого перезапуска приложения заявка
остаётся в последнем статусе, вся история — на вкладке «История статусов».

## Сценарий 2 — Отказ и повторная подача

1. Клиент подаёт заявку с суммой выше лимита продукта и DTI > 35% (например,
   12 000 000 ₽ при выручке 3 000 000 ₽, «Краткосрочное финансирование»).
2. Банк проводит проверки → индекс качества низкий, блокирующие сигналы R-02, R-06.
3. Старший аналитик фиксирует «Отклонена» с основанием.
4. Статус «Отклонена» — терминальный; данные и аудит сохраняются.
5. Клиент снова подаёт заявку с тем же ИНН — теперь она **создаётся** (ограничение
   действует только на активные дубли): новая заявка, новый номер.

## Сценарий 3 — Запрос уточнений и возврат на обработку

1. Демо-заявка «ООО «Тёплый хлеб»» — статус «Нужны уточнения», клиенту показан
   текст запроса.
2. Клиент прикладывает файл и пояснение, отправляет уточнение.
3. Статус меняется на «Сбор данных» (ENRICHMENT), в аудите —
   `CLIENT_CLARIFICATION_SUBMITTED`; заявка снова видна банку в активной очереди.

## Сценарий 4 — Встречное предложение

1. Демо-заявка «ООО «ТехноПарк-Юг»» — «Одобрена с условиями» (сумма снижена на 10%).
2. Клиент видит условия и принимает встречное предложение → ACCEPTED → подписание → выдача.
   Отклонение — заявка закрывается как REJECTED с причиной «клиент отклонил».

## Сценарий 5 — То же через API (Swagger/Postman)

1. Открыть <http://localhost:8000/docs> или импортировать `postman_collection.json`.
2. Пройти шаги сценария 1 теми же запросами: заголовок `X-Demo-Pin: 1234`
   (клиентские шаги 2–3, 8–12) и `X-Demo-Pin: 0007` (шаги 4–7).
3. Недопустимый переход (например, сразу `SUBMITTED → DISBURSED`) возвращает
   409 со списком допустимых статусов — карта переходов едина для UI и API.

## Что считается успехом

Каждый сценарий заканчивается терминальным статусом (DISBURSED/REJECTED),
все переходы — по карте состояний, каждое решение снабжено основанием,
каждое действие попадает в журнал аудита.
